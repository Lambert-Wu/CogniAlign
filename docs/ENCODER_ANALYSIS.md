# 跨语言用的嵌入模型分析（2026-10-04）

> 本文**不新增实验**，只把「你项目里实际在用的编码器」和「已跑出来的实测数字」对起来看。
> 数据来源：`docs/CROSSLINGUAL_DIAGNOSIS.md`、`logs/probe_crosslingual_all.log`、
> `modules/configs/*.yaml`、`models/` 下的本地模型卡。
>
> 标注约定：**【实测】**= 本项目跑出来的数；**【模型卡】**= 官方公开的模型信息；
> **【推断】**= 由前两者推导，尚未实测。

## 一句话结论

**你现在缺的不是"更会中文的编码器"，而是"两侧必须走同一个编码器"这条底线。**
实测：同一个 XLM-R 两边用 → 文本跨语言 0.615；而 `legacy` 那套「train 用英文
DistilBERT、test 用 bert-base-chinese」是**两个完全不相干的模型**，文本跨语言 **0.253**
（区间 `[0.158, 0.350]`，整段在 0.5 以下）—— 那不是"迁移得差"，那根本不是迁移。

同时：**"多语言"并没有带来优势**。文本侧 XLM-R/XLM-R → 0.615，而"train 用 DistilBERT、
test 用 bert-base-chinese"那套是**两个不相干的模型**接在一起 → 0.253（整段 < 0.5）。
**"共享同一个" 比 "会用中文" 重要。**

> ⚠️ 本文第一版还写过"纯英文 wav2vec2 音频 0.625 高于多语言 XLS-R 0.599，所以多语言没用"。
> **这条已撤回**：那 0.026 的差在 n=80 下测不出来，而且 wav2vec2 那格数据是坏的
> （音频只覆盖 56% 内容、与 `feat_distil` 音频逐字节相同、对齐检查不通过）。
> 控制"说话长短"后 XLS-R **0.686** > wav2vec2 **0.606**，正好反过来。

## 二、逐个分析

### 1. `distil`（DistilBERT，纯英文）—— 跨语言场景下**结构性不可用**

- **语言覆盖**【模型卡】：只有英文。词表是英文 WordPiece（30522）。
- **中文侧的表现**：中文文本进这个分词器，绝大多数汉字会落到 `[UNK]`。
  参考**实测**：本项目为 XLM-R 补了 7 个生僻字（`rare_char_map`：锨镊鳊笤鲈獭荠）；
  对 distil 而言缺的远不止 7 个 —— 中文整段基本无法表示。
- **实测表现**：英文内部 5 折 0.854（很好）；作为**跨语言**的一端 → 只能配上
  `chinese`，得到 **0.253**。
- **判定**：**不要出现在任何跨语言实验里**。它在 `legacy_*` 里的角色是"英文单语基线"。

### 2. `chinese`（bert-base-chinese，纯中文）—— 只能做中文内部对照

- **语言覆盖**【模型卡】：中文为主；英文能力弱且与英文模型空间无关。
- **实测表现**：中文内部 5 折 **0.895**（`legacy` 配置的文本），中文内部训出来的
  完整模型曾达 **78.8% / AUC 0.900**（`chinese_internal_cv.yaml`）。
- **判定**：它是"中文天花板参照"的正确工具，**但和英文侧配不成对**。
  用在跨语言里 = 把两个不同坐标系的特征喂给同一个分类头。

### 3. `xlmr`（XLM-R base，多语言）—— **唯一现实中能用于跨语言的文本编码器**

- **语言覆盖**【模型卡】：100 种语言，中英文都在内。
- **分词特点**【模型卡+实测】：SentencePiece，中文基本按字切。
  **实测 token 数**：中文中位 **270**、英文中位 **138**（同一套 512 的长度上限下）。
- **实测表现**：英文内部 0.844 ／ 中文内部 **0.952**（中文侧非常强），
  跨语言（XLM-R↔XLM-R）**0.615**，加按语言标准化后 0.647。
- **判定**：**当前正确的默认选择**。但要说清它的局限：XLM-R 是**纯 MLM** 训练的，
  没有平行语料/翻译目标，所以它的跨语言对齐是"顺带的"，不是专门优化过的 ——
  这解释了为什么它能到 0.6 却上不去（0.6 也就比瞎猜好一点点）。

### 4. `wav2vec2`（base-960h，纯英文音频）—— 意外地够用

- **语言覆盖**【模型卡】：LibriSpeech 960 小时，**纯英文**。
- **实测表现**：英文内部 0.835 ／ 中文内部 0.876（抽特征本身在中文上也成立），
  **跨语言 0.625**（加标准化 0.662）—— 全表最高的音频跨语言成绩。
- **为什么纯英文模型也能跨？**【推断】音频侧真正迁移的是
  **韵律/声学属性**（语速、停顿、嗓音质量），这些是跨语言共通的；
  而且**两侧走的是同一套权重**，所以特征在同一个坐标系里，下游头学的方向还有意义。
- **判定**：**够用，不必换**。这是本项目里"多语言不是必需"的最强证据。

### 5. `xlsr`（XLS-R-300m，多语言音频）—— 换了，但**没带来增益**

- **语言覆盖**【模型卡】：128 种语言、43.6 万小时，**包含中文**。
- **实测表现**：英文内部 0.778 ／ 中文内部 **0.959**，跨语言 **0.599**（标准化后 0.592）。
  **中英可分性 0.997**（比 wav2vec2 的 1.000 略低）。
- **两个反直觉的点**：
  1. 它**确实**更语言无关（可分性 0.997 < 1.000），**但迁移没有更好**（0.599 < 0.625）
     → **"表示更语言无关" ≠ "跨语言迁移更好"**，至少在这份数据、这个头上不成立。
  2. 它是 **1024 维**，比 hidden_size(768) 大 → 网络必须多挂一层投影
     （`audio_projection_kind()` → `'linear'`），那是 **1024×768 = 78.6 万个随机初始化参数**，
     却只有 188 条训练样本去学。`xlmr_xlsr_pca.yaml` 就是为了绕开这层才做的 PCA，
     实测两者跨语言差异（0.599 vs 0.592）落在噪声里。
- **判定**：**当前没有理由优先它**。要换多语言音频模型，前提是**两侧一起换**，
  而且要接受"重提特征 + 可能多一层投影"的代价。

### ⚠️ 更正：「XLS-R 跨语言不如纯英文 wav2vec2」这条**站不住**（2026-10-04）

上面 §5 写的"0.599 < 0.625，换了没赚到"，**证据不足以支撑这个结论**。三条理由：

**① 0.026 的差，本来就没测出差别。** n=80，两组 95% 区间几乎完全重合：

| 音频编码器 | 跨语言 AUC（none） | 95% 区间 |
|---|---|---|
| XLS-R（`default`） | 0.599 | [0.461, 0.721] |
| wav2vec2（`xlmr_wav2vec2`） | 0.625 | [0.497, 0.754] |

**② wav2vec2 那一格的数据本身是坏的，不该参与对比。** 三条独立证据：

- 中文音频**有效行数中位只有 148、最大 294**，而同一条录音的文本 token 中位是 **270**、
  最大 512。音频是按 token 对齐的（每字一行），148 ≪ 270 意味着**这条音频只覆盖了
  56% 的内容，后半段直接是零**。对照 XLS-R 那套：音频有效行中位 **269**，和文本 270 对得上。
- `logs/probe_crosslingual_all.log` 里，`xlmr_wav2vec2` 与 `legacy_distil_wav2vec2` 的
  **audio 列逐位完全相同**（0.625 / 0.662 / 去长度 0.606 / 置换 0.457±0.129）——
  探针只读音频，这说明**两套配置读的是同一份音频文件**（`feat_xlmr_wav2vec2` 的音频
  ＝ `feat_distil` 的音频）。
- `check_alignment.py` 对 `xlmr_wav2vec2.yaml` 判 **train 229/235、test 80/80 不通过**
  （`default.yaml` 是 235/235、80/80 通过）。

更可疑的是**置换对照**：wav2vec2 的 audio 是 **0.457**（**低于 0.5**，方向反了），
XLS-R 是 0.525（正常）。一份干净的特征，打乱标签后应该落在 0.5 附近。

**③ 唯一干净的口径下，XLS-R 反而更高。** 把"说话长短"这个混淆项线性剔除后再测：

| 音频编码器 | 原始 | **去长度后** |
|---|---|---|
| **XLS-R** | 0.599 | **0.686** |
| wav2vec2 | 0.625 | **0.606** |

去掉长度后两条线**交叉**：XLS-R 反超 0.08。而中文侧"说话长短"单独就能排标签到 0.634~0.655，
所以**不去长度就比跨语言，等于在比谁更被长度绑架**。

> 结论修正为：**这份数据上没有证据表明 XLS-R 比 wav2vec2 差；在控制长度后反而是 XLS-R 更高。**
> 但**也不能**据此宣称 XLS-R 更好 —— 因为左边的数来自一份已证污染的特征。

### 就算数据都干净，XLS-R 也不会"遥遥领先"（三条机制）

用户的直觉（XLS-R 预训练规模大得多，应该更强）本身没问题，但它落在**这个任务 + 这个评测方式**上会被削弱：

1. **"多语言"≠"跨语言对齐"。** XLS-R 和 XLM-R 一样是**纯自监督**预训练，
   **没有平行语料、没有跨语言对齐目标**（模型卡）。"支持 128 种语言"只意味着
   同一个模型能处理这些语言，**不意味着**它把中英映射到同一片空间。
   实测佐证：中英可分性 **0.997**（XLS-R）/ 1.000（其余），两边特征几乎线性可分。
2. **`wav2vec2-base-960h` 是做过有监督微调的**（模型卡：LibriSpeech 960h + CTC），
   它被显式逼着学**英文音素判别**——而 AD 检测关心的正是"发音是否异常"。
   实测：英文内部音频 **wav2vec2 0.835 > XLS-R 0.778**。纯自监督的 XLS-R 表示更"通用"，
   但在"判别发音异常"这件事上不一定更锋利。
3. **维度吃亏（推断，未实测）**：XLS-R 是 **1024 维**、wav2vec2 是 768 维，而这边的探针
   只有 **235 条**训练样本。维数越高、同正则下越难过拟合与估准方向。
   **要排除这条，必须把两者 PCA 到同一维再比**（还没做）。

### 要真正比出高下，需要四件事

1. 先在服务器确认/重提 `feat_xlmr_wav2vec2` 的音频（见 `CROSSLINGUAL_DIAGNOSIS.md` 文末）；
2. 两个编码器输出 **PCA 到同一维度**（比如都 768）；
3. **统一去长度后**再比（长度是显式混淆项）；
4. 因为两个探针是在**同一批 80 条中文**上测的，应该做**配对**比较
   （对同一批样本做配对 bootstrap / DeLong），而不是只看两组区间是否重叠。

## 三、三条结构性结论

### 结论 1：跨语言的底线是"两侧共享同一个编码器"，不是"编码器得多语言"

| 搭配 | 两侧是不是同一个模型 | 跨语言 AUC【实测】 | 去长度后 |
|---|---|---|---|
| XLM-R / XLM-R | ✅ 是（而且是多语言） | **0.615** | 0.640 |
| wav2vec2 / wav2vec2 | ✅ 是（**纯英文**模型） | 0.625 ⚠️数据有污染 | 0.606 |
| XLS-R / XLS-R | ✅ 是（多语言） | 0.599 | **0.686** |
| DistilBERT / bert-base-chinese | ❌ **两个不同模型** | **0.253** | 0.148 |

四行连起来读：**有没有共享权重，决定了能不能跨；是不是多语言，几乎不影响。**
⚠️ 后两列不要混读：横着看"谁更强"时**必须用去长度那一列**（长度在中文侧单独就能排到 0.63~0.66，
不控制就等于在比谁更被长度绑架）；而 wav2vec2 那一行两列都要打折看（数据有污染，见 §5 更正）。

【推断】机制：编码器是冻结的。下游那个头（融合层+分类器）学的是
"在**这个编码器输出空间**里，往哪个方向走算有病"。只要两侧走同一个函数，
中文特征即使"没见过"，也仍落在同一个坐标系里，学到的方向还能用一点；
换了第二个模型，中文特征落在**另一个互不相干的坐标系**，
头的权重就没有任何理由成立 —— 实测的 0.253（系统性反向）正是这个现象。

### 结论 2：`legacy_*` / `paper_*` 里的"中文 test"数字，不是跨语言迁移

- 那 9 份配置写的是 `split_textual_model.test: chinese` ——
  **train 用 DistilBERT 抽特征、test 用 bert-base-chinese 抽特征**。
- 于是 `RESULTS.md` 里中文 test 表的 `distil_wav2vec2_pause`（acc 63.7% / AUC 0.707）
  这一行，**严格说不是"英文训→中文测"**，而是"英文特征上训的头，拿去读中文特征"。
- 而我的探针在同一对特征上量到的是 **0.253**，比 0.707 低得多。
- **这个差异本身值得追**（见下面"待验证的假设"）。

### 结论 3：一个被忽略的放大器 —— 中英 token 数差一倍

【实测】同一套特征、同一个 `max_length=512`：

| 语言 | 文本 token 中位 | 用满了多少格子 |
|---|---|---|
| 英文 | 138 | **27%** |
| 中文 | 270 | **53%** |

**中文的填充比例只有英文的一半。** 而现有网络的池化是 `src.mean(dim=1)`
**不带掩码** —— 也就是把填充行一起平均了。填充比例差一倍 →
**同一个池化操作对中英两侧产生的偏移量天生不同**。
【推断】这正好是"跨语言分数整体平移"的一个现成来源：它不需要模型学错，
只要多平均了几行就会产生一条与语言绑定的偏移。
（`docs/CROSSLINGUAL_DIAGNOSIS.md` 的"掩码池化"一节已量化过稀释幅度；
`RESULTS.md` 里掩码池化是第一个多种子方向一致的增益，+0.008 量级。）

## 四、待验证的假设（都不需要新编码器，但需要跑一次训练）

1. **`legacy` 文本那 0.707 里，有多少是"填充泄漏"？**
   【推断】不带掩码的池化会把"填充比例"混进特征，而填充比例 ≈ 说话长短，
   说话长短在中文上单独就能排标签到 **0.655**。所以一个"多平均了几行"的模型，
   可能白捡了一条长度信号。
   **验证办法**：把 `legacy` 的模型换成掩码池化重训一次，看中文 AUC 掉不掉。

2. **XLS-R 的"更语言无关"能不能转化成迁移？**
   【推断】现在两者都挂在同一类头下面，且样本只有 80 条，差异在噪声里。
   若要试，应在**掩码池化 + 多种子**的条件下比，而不是单跑。

3. **XLM-R 的 0.615 是"对齐"还是"长度"？**
   【推断】剔掉长度后文本从 0.615 → 0.640（+0.025，正向），说明**不是**长度造出来的，
   但也说明 XLM-R 的对齐确实很弱。

## 五、如果你确实想换更强的跨语言文本编码器

**要选"专门为跨语言对齐训过"的模型**，而不是"多语言 MLM"：

| 方向 | 候选 | 代价 |
|---|---|---|
| 句级对齐模型 | LaBSE、multilingual-e5、LASER、SONAR | ⚠️ 输出的是**句向量**，而你现在的架构依赖**词级对齐的 token 序列**（论文的核心就是词级对齐）。改成句级等于换掉论文方法。 |
| token 级多语言 | XLM-R large、mDeBERTa-v3、XLM-V | 维度/显存上升，仍需重提特征；对齐度提升有限（都还是 MLM 系）。 |
| 音频 | XLS-R-1B/2B | 显存；且本实验表明"多语言音频"并未带来增益，优先级低。 |

**我的建议**：**先别换编码器。** 同语种内部已经是 0.89~0.96，跨语言 0.6 ——
差距不在"编码器会不会中文"，而在"两侧的分数分布不对齐"（整体平移 + 长度混淆）。
换编码器解决不了这个，先做**掩码池化 + 同一编码器 + 长度控制**那次单变量实验更划算。

## 附：如果你问的是"嵌入模型**之后**那一层"

那一层的问题在 `docs/CROSSLINGUAL_DIAGNOSIS.md` 里已经量化过，摘要：

- **训练的融合头跨语言（0.46~0.52）不如一个线性探针（0.615~0.719）** → 头在过拟合英文。
  （⚠️ 前提未排除：探针用了**掩码池化**、现有模型**没有**，所以这 0.1 里有一部分是池化差异。）
- **1024→768 的投影层**（XLS-R 那套）是**随机初始化**的 78.6 万参数，只有 188 条样本去学；
  PCA 版本正是为了绕开它（实测差异在噪声内）。
- **门控融合**被证明"工作点冻结在初值、被后面的 FFN 吸收"（见 `RESULTS.md`）。
- **池化不带掩码**（见上文结论 3）。
